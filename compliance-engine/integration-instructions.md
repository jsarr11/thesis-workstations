# Integration Guide

> Τι πρέπει να κάνει μια πλατφόρμα για να χρησιμοποιήσει το Compliance Engine.

**Κατάσταση:** σχέδιο (draft). Το API και οι ρυθμίσεις θα οριστικοποιηθούν κατά την υλοποίηση· ό,τι σημειώνεται ως *(σχέδιο)* μπορεί να αλλάξει.

---

## 1. Προαπαιτούμενα

- Kubernetes cluster (δοκιμασμένο σε k3s).
- Δικαίωμα δημιουργίας namespace και ServiceAccount για το εργαλείο.

## 2. Εγκατάσταση του εργαλείου *(σχέδιο)*

Το εργαλείο εγκαθίσταται στο δικό του namespace (`compliance`) και δεν μοιράζεται τίποτα με την πλατφόρμα.

```bash
kubectl apply -f compliance-engine.yaml
```

## 3. Σύνδεση της πλατφόρμας

Υπάρχουν δύο τρόποι, που μπορούν να χρησιμοποιηθούν και μαζί.

### 3.1 API: έλεγχος πριν από το deploy *(σχέδιο)*

Η πλατφόρμα στέλνει το manifest πριν το κάνει deploy και χρησιμοποιεί αυτό που επιστρέφεται.

```
POST /evaluate
Authorization: Bearer <API key>
```

```json
{
  "manifest": { "apiVersion": "v1", "kind": "Pod", "...": "..." },
  "profile": "developer"
}
```

Απάντηση:

```json
{
  "compliant": true,
  "manifest": { "...": "το διορθωμένο manifest, έτοιμο για deploy" },
  "findings": [
    { "rule": "A.8.9", "cis": "5.2.3", "found": "hostPID: true", "action": "REMEDIATED", "result": "hostPID: false" }
  ]
}
```

- `compliant: false` σημαίνει ότι κάτι δεν μπορούσε να διορθωθεί αυτόματα. Η πλατφόρμα **δεν** κάνει deploy.
- Η πλατφόρμα κάνει deploy **το manifest της απάντησης**, όχι το αρχικό.
- Τα `findings` μπορούν να εμφανιστούν στον χρήστη και να γραφτούν στο audit της πλατφόρμας.

### 3.2 Admission webhook *(σχέδιο)*

Όταν είναι ενεργό, το εργαλείο ελέγχει ό,τι μπαίνει στο cluster, ακόμα κι αν η πλατφόρμα δεν το καλέσει. Δεν χρειάζεται αλλαγή στον κώδικα της πλατφόρμας, μόνο οι ρυθμίσεις της ενότητας 4.

## 4. Ευθύνες της πλατφόρμας

Όσα **δεν** κάνει το εργαλείο και πρέπει να φροντίσει η πλατφόρμα:

| Τι | Γιατί | Κανόνας |
|---|---|---|
| Τα workloads να μην τρέχουν στο `default` namespace | Το webhook μπορεί μόνο να απορρίψει, όχι να αλλάξει namespace | A.8.31 |
| Ο ServiceAccount της πλατφόρμας να δηλωθεί στο εργαλείο ως εγκεκριμένος | Αλλιώς ο κανόνας GitOps θα μπλοκάρει την ίδια την πλατφόρμα | A.8.32 |
| Hardening των images στο build (non-root, χωρίς sudo, pinned εκδόσεις) | Το εργαλείο ελέγχει τα images, δεν τα ξαναχτίζει | A.8.28, A.8.2 |
| Υπογραφή των images (Cosign) | Ο κανόνας απορρίπτει ανυπόγραφα images | A.8.4 |
| Ingress με TLS, αν εκτίθενται υπηρεσίες | Το εργαλείο ελέγχει τη ρύθμιση, δεν εγκαθιστά certificates | A.8.24, A.8.21 |
| Ενεργό audit logging στο cluster | Το εργαλείο το ελέγχει, δεν αλλάζει τις ρυθμίσεις του k3s | A.8.15 |

## 5. Αν το εργαλείο δεν είναι διαθέσιμο

Προεπιλογή: **fail-closed**. Αν το εργαλείο δεν απαντά, το deploy δεν γίνεται. Ένα workstation που δεν ελέγχθηκε δεν παραδίδεται στον χρήστη.

## 6. Παράδειγμα: η πλατφόρμα της διπλωματικής (`manager/`)

Αλλαγές που θα χρειαστούν στον Manager *(θα συμπληρωθεί κατά την υλοποίηση)*:

- [ ] Ρύθμιση στο `manager/.env`: διεύθυνση και API key του εργαλείου.
- [ ] Stage 2 του pipeline (`workstations.js`): κλήση του `/evaluate` και deploy του manifest της απάντησης.
- [ ] Εμφάνιση των ευρημάτων στο UI και καταγραφή τους στο `audit_logs`.
- [ ] Αφαίρεση της καρτέλας «Policies» από το `/admin` (οι κανόνες διαχειρίζονται πλέον στο UI του εργαλείου).
- [ ] Workstations σε δικό τους namespace αντί για `default` (A.8.31).
- [ ] Δήλωση του ServiceAccount του Manager ως εγκεκριμένου (A.8.32).
